## Cadence Rules (what makes something "lingering")

### Primary signal: live file mtimes, not frontmatter `last_touched`

**Do not trust the `last_touched` frontmatter field as the source of truth for staleness.** Patrick has said directly he'll rarely remember to update it by hand, and it's already been caught drifting: on 2026-08-08, seven new Clinical Reasoning episode notes (CPS 146, 160, 167, 174, 175, 179, 186) were added to `Clinical Reasoning/Episodes/` between 9:22–10:17pm, but `Projects/Clinical Reasoning.md`'s `last_touched` still read 2026-07-26 and the MOC hadn't been touched since 2026-07-25 — real work happened, and the tracking field never moved. Treat `last_touched` as narrative color in the Log, never as evidence of inactivity on its own.

The actual "last acted on" date for a domain is the **most recent file mtime** across the files that make up its real work product — checked live (`device_list_dir`, not a cached listing) before concluding anything is stale:

- **Project coordination initiatives**: max mtime across the project note in `Projects/`, every file listed in its `related` frontmatter, and any dedicated content folder (e.g. Declutter's supporting reference notes).
- **Clinical Reasoning**: max mtime across *everything* in the `Clinical Reasoning/` folder — MOC, indices, and all files in `Episodes/` — **and `Curbsiders Episodes/`, which is a separate top-level folder**. Checking only `Projects/Clinical Reasoning.md` will miss real activity, since episode work routinely doesn't touch that note at all. Used for reporting only; the domain is untracked.
- **Meal Planning**: the Todoist task's completion history — already live via the connector, no file check needed.
- **Financial Planning**: the "Weekly finance review" task's completion history, plus the most recent file in `Finances/Weekly/`.
- **Logbook**: the most recent filename in `Logbook/Daily/`.
- **Week Ahead**: the most recent filename in `Projects/Week Ahead/` (check `Archive/` too if the current week hasn't triggered yet).

If a frontmatter `last_touched` date and the computed file-mtime date disagree, say so explicitly rather than picking one silently — that mismatch is itself worth surfacing (it usually means work happened somewhere the tracking note doesn't know about yet).

### Opt-out: `cadence: untracked`

**A project whose frontmatter carries `cadence: untracked` has no expected rhythm and must never be flagged as stale, lingering, behind pace, or overdue.** Report its real last-touched date if asked; do not compute or present a days-since figure, and do not surface it in any "what's lingering" answer. Currently: `Projects/Clinical Handbook.md` (set 2026-08-23) and `Projects/Clinical Reasoning.md` (set 2026-09-21) — see Decisions log. This exists because the staleness machinery measures *drift from an expected cadence*, and a project that was never given one will otherwise generate a permanent false 🔴.

**Domains with no project note carry their opt-out in the mapping table.** CTIs, Bedside Notes, and Garden are untracked per the table above and are exempt from every staleness rule, exactly as `cadence: untracked` is.

### Gates: `gated_until` + `gate`

A project that cannot move until a known date carries `gated_until: YYYY-MM-DD` and a one-line `gate:` naming what it waits for. Before that date it is shown 🚦 and never flagged; after it, days-since counts from the gate date, so an unmet gate flags on the normal 4/7-day schedule. A gate must carry a date; open-ended waiting on a person is `status: waiting`.

### Secondary proxies (still useful on top of the mtime check)

- **Sequenced/recurring tasks with a counter** (e.g. Declutter's "Week X/37"): expected pace is 1 unit per calendar week from the task's start date. Flag if elapsed weeks since start exceeds the counter — i.e., behind pace. **Declutter restarted 2026-08-26 at Week 1/37 on a fixed Wednesday 8:00pm anchor** (the original 2026-08-08 Saturday start never ran a single session and was retired — see Decisions log), so counting runs from 8/26: by week N the counter should read N. **A `shelved` status suspends the counter** — a shelved project is exempt and must never be flagged behind pace, whatever the counter reads. On revival the counter resumes from the new restart date, not the original anchor. (Declutter has been shelved since 2026-09-08; the counter is suspended.)
- **No due date + old creation date**: for any task carrying a `prj-<slug>` label, flag if it has no due date and was created more than ~2 weeks ago — it's gone quiet.
- **Repeatedly rescheduled tasks**: not overdue, but functionally stagnant. Check via `find-activity` for reschedule events on labeled tasks; flag at 3+ reschedules.
- **Meal Planning**: flag if the "Plan meals for the week" recurring task is still open past Sunday night.
- **Financial Planning**: flag if the "Weekly finance review" task is still open past Sunday night.
- **Logbook**: expect a daily note for every day. Flag if the most recent file in `Logbook/Daily/` isn't dated today or yesterday.
- **Weekly Handoff vs. rollup** (see 2026-09-21 decision): flag a missing or empty `## Handoff Note` in the current `Logbook/Weekly/YYYY-Www.md` — that one is required and blocks the Week Ahead. **Never flag `## Weekly Rollup` as missing, pending, stale or behind**; it is deferrable by design. Likewise, a Week Ahead note carrying `handoff_source: provisional` is a designed state, not a failure — flag only if it is still unreconciled past Wednesday.
- **What goes in the Handoff's Open items** (2026-09-24 decision): only items with an action for Patrick or a dated gate. Anything waiting on someone else with nothing for Patrick to do goes in a separate `## Waiting on others (review only)` section of the weekly note, outside the Handoff, so neither the homepage nor the Week Ahead reads it as a to-do. Do not assume a follow-up is needed; carried "no action unless they move" lists are not kept.
- **Untracked projects and domains**: exempt from every rule in this section. See the opt-out above.
